Multiplayer Agent Sessions

Build specification. Four tasks, four candidate models per task, one documented winner each, selected through a shared evaluation harness. This document defines the system, the contracts, the candidate matrix, and the per-person build packages. It is written to be handed directly to a coding agent alongside one person's package.

System

A shared live session in which several humans and several agents work in one workspace with concurrent edits, hand-off, interruption and rollback. Four learned models sit on the platform. One published baseline is reproduced separately.

Capabilities

CapabilityDefinitionAcceptance test
Concurrent editTwo humans and one agent change the same document simultaneously without lost updatesScripted concurrent-edit test: 3 writers, 200 ops, final state converges on all clients
Hand-offA running agent task transfers to another participant, who receives a generated session summaryHand-off produces a handoff event and an M1 summary within 5 s
InterruptionAny participant stops a running agent mid-task and redirects itAgent halts within 2 s, session state consistent, interrupt event logged
RollbackSession rewinds to any prior sequence numberReplay test: state rebuilt from events alone equals live state
AttributionEvery agent action is attributable to the participant whose instruction caused itEvery agent_step event carries a non-null causality.root_instruction

Non-goals

  • Production authentication. Sessions use a join code and a display name.
  • New CRDT algorithm. Yjs is used as a library and treated as correct.
  • Mobile app, offline mode, internationalisation.
  • Open-ended agent tool use. Five fixed tools, defined in section 5.
  • Horizontal scaling. One server process, 8 participants per session, 5 concurrent sessions.
  • Full fine-tuning above 4B parameters. LoRA adapters only.

Checkpointing

All training writes LoRA adapters or encoder weights under 500 MB. Every training script implements:

  • --save_steps 200, pushing the adapter to remote storage on each save
  • --resume_from_checkpoint <remote-uri>, restoring optimizer state and step count
  • Base weights re-downloaded from Hugging Face on every run; nothing large persists on local disk

Implemented once in models/common/checkpointing.py and imported by all five training scripts.

Conventions

  • Branches: <owner>/<linear-id>-<slug>, for example naman/DAT-42-freeze-m2-split.
  • main is protected. One approving review, from the owner of any directory the change touches.
  • Commit messages start with the Linear issue id.
  • Any change to a schema, an API route or a metric definition requires an ADR in docs/decisions/.
  • Python: type hints throughout, ruff clean, line length 100.
  • TypeScript: strict mode, no any.

Data contracts

Defined once in session-service/app/schemas.py as Pydantic v2 models, exported to openapi.json, and generated into TypeScript for the client. Changing one requires an ADR.

SessionEvent

Every action in the system becomes exactly one SessionEvent, appended to Postgres and broadcast over WebSocket. The event log is the audit trail, the input to replay, and the training data for M2, M3 and M4. No state mutation occurs except by appending an event.

Anonymisation

data/scripts/anonymise.py runs before any session data is committed. It replaces actor.display_name with p_1 .. p_n per session, strips any free-text occurrence of those names from payloads, and rewrites actor.id consistently within the session. Output is written to data/sessions/raw/; the un-anonymised source never enters the repository.

Evaluation harness

One entry point for all 20 candidates. Built by Pramod in eval/, which he owns exclusively. No evaluation loop, metric implementation or seeding logic exists anywhere else in the repository.

Command surface

# run one candidate on all three seeds
python eval/harness.py --task m2 --candidate m2-c --seeds 13,29,47 --split seed

# run every candidate for a task
python eval/harness.py --task m2 --all --seeds 13,29,47 --split real

# emit the comparison table and mark the winner
python eval/compare.py --task m2 --split real --out docs/tables/m2_bakeoff.md

# 20-example smoke run, no training, used in CI and before demos

Protocol rules the harness enforces

  1. Split is loaded from split: in the config and is read-only. The harness refuses to run if the split directory has uncommitted changes.
  2. Seeds are set through eval/seeding.py for Python, NumPy, PyTorch, CUDA and the dataloader worker init.
  3. effective_batch_size is held constant within a task by adjusting gradient accumulation to the per-device batch that fits.
  4. Prompted candidates read their prompt verbatim from prompt_file. No prompt strings inline in code.
  5. Latency is measured over 100 single-example forward passes after 10 warm-up passes, on the hardware named in hardware.
  6. Every run records git_sha and model_revision. A result without both is invalid.
  7. split is always written and always appears in the caption of any generated table.

Candidate matrix

Twenty candidates. Four per task plus four baseline judge arms. Each task includes at least one untrained or non-neural candidate as the floor.

Session collection

  1. Six fixed scenario briefs, committed in data/scenarios/. Each brief assigns at least two participants partially conflicting sub-goals.
  2. Per session: 3 to 4 human participants, 2 agents, 20 to 30 minutes.
  3. Captured automatically as the event log. No audio, video or screen recording.
  4. export_sessions.py pulls events from Postgres to data/sessions/raw/<session_id>.jsonl.
  5. anonymise.py replaces display names with p_1 .. p_n before anything is committed.
  6. Two annotators label every example independently in tools/annotator/. Cohen's Kappa written to data/sessions/annotated/AGREEMENT.md.
  7. make_splits.py --by session --seed 13 produces train, validation and test. Splits are committed and never regenerated.

Targets: 30 sessions, 800 labelled instructions, 250 conflict cases.

Build order

  1. Repository foundation. requirements.txt with the pins in section 2, pip freeze > requirements.lock.txt, .python-version, .nvmrc, directory skeleton, branch protection, CI running ruff, mypy and pytest.
  2. Schema. Implement every contract in section 4 as Pydantic v2 models in app/schemas.py. Export openapi.json. Generate TypeScript types into client/src/lib/api.ts. Commit and announce; the rest of the team codes against this.
  3. Event log. Postgres tables, alembic migration, append-only insert with monotonic seq allocated inside a transaction per session. Reject writes that attempt to mutate an existing row.
  4. Permissions. Role per participant, checked on every event append. Rejected actions are still logged as type: rejected.
  5. Replay. app/replay.py rebuilds full session state from events alone, given a to_seq. Rollback endpoint uses it.
  6. WebSocket fan-out. Redis pub/sub, one channel per session, delivering every appended event to subscribers.
  7. Serving. serving/serve.py implementing the uniform predict interface. Stub adapters for m2, m3 and m4 that return fixed valid responses, so teammates can integrate before their models exist.
